## Critical

- **Tracking links are broken in production.** `LinkTracker.replaceMessageContentWithTrackedLinks` writes `${baseURL}/r/${id}`, but `app.ts` only serves `/t/:id` — there is no `/r/` route anywhere in the repo. Every tracked link in a sent campaign is a 404 (it falls through to the SPA catch-all). Tests assert the current behaviour of each side.
- Related: `/t/:id` only records a click when a `?sid=` subscriber id is present, but `LinkTracker` never appends one. Even with the route fixed, clicks would not be attributed to a subscriber.
- **Scheduled campaigns never send.** `campaign.start` sets a future-dated campaign to `SCHEDULED`, but nothing anywhere transitions `SCHEDULED` → `CREATING`, and `processQueuedCampaigns` only reads `CREATING`. The campaign sits in `SCHEDULED` forever with no messages. Tests pin the current (broken) behaviour.
- **The REST API re-subscribes people who unsubscribed.** `POST /api/subscribers` (existing email) and `PUT /api/subscribers/:id` in `src/api/server.ts` rebuild memberships with `ListSubscribers: { deleteMany: {}, create: ... }`, recreating every row with `unsubscribedAt = null`. A signup-form re-submit silently puts someone back on every list they left, and erases the unsubscribe history. Contradicts `docs/unsubscribes.md`.

## High

- **`user.signup` refuses to create a second account.** It throws `BAD_REQUEST` if `prisma.user.count()` is non-zero, so the instance is permanently single-user with no invite/team flow, and the duplicate-email check immediately below it is unreachable dead code. If multi-user was intended, this is the blocker.
- `authenticateApiKey` never checks `ApiKey.expiresAt`. The column exists, the settings UI sets it, but an expired key authenticates exactly like a live one. Tests pin the current behaviour.
- `settings.createWebhook`, `deleteWebhook` and `listWebhooks` are TODO stubs — they return `{ webhook: null }`, `{ success: true }` and `[]` with the real implementation commented out, while a full `Webhook` model and a separate `webhookRouter` exist. The settings UI silently no-ops.
- `sendMessages` marks a message `PENDING` before sending and never resets it if the process dies mid-send; a crashed run leaves messages stranded in `PENDING`, which no query ever picks back up.
- The CI workflow has never actually run (and `docs/testing.md` documents it as written, not as run) — there was no GitHub access from the authoring environment, so the first real push is the first real test of it.
- A commit `d3c5f46 "Phase 1: Test harness hardening"` appeared on `chore/adding-tests` without the loop running `git commit` — something in the environment (a hook or wrapper) committed the working tree mid-phase. Worth checking why, since the loop is supposed to leave all changes uncommitted.
- **Subscribers can be attached to another organization's lists.** `subscriber.create` (`listIds` → `connect`), `subscriber.update` (`listsToAdd`) and `subscriber.import` (`input.listId`) in `src/subscriber/mutation.ts` never check the list belongs to the caller's org. Campaign recipient selection doesn't filter by subscriber org either, so org B's campaigns would mail org A's addresses through org B's SMTP. The REST endpoints do check. Only reachable with more than one user.
- `settings.testSmtp` has no org-membership check: it loads `smtpSettings` for any `organizationId` passed in and sends to a caller-chosen address, so any logged-in user can send mail through another org's SMTP account. A test pins the current behaviour.
- `user.login` selects `password` and `pwdVersion` (overriding the global `omit`) and returns the whole `user` object, so every login response carries the bcrypt hash.
- **Cancel and unsubscribe lose to an in-flight send.** `sendMessages` sets each message to `PENDING` with an unconditional `update({ where: { id } })` just before sending, overwriting a `CANCELLED` set in the meantime; the email still goes out.
- Cancelling a campaign in `CREATING` doesn't stop it: messages from an uncommitted `processQueuedCampaigns` batch transaction land as `QUEUED` after the cancel and are sent (`sendMessages` never checks campaign status), and the batch's unconditional `campaign.update({ status: "SENDING" })` flips a `CANCELLED` campaign back to `SENDING`.
- No `List-Unsubscribe` / `List-Unsubscribe-Post` headers: `Mailer.sendEmail` can't set custom headers and there is no RFC 8058 one-click endpoint. Gmail and Yahoo require this for bulk senders, so campaigns risk spam-foldering or rejection.
- The webhook sandbox's hand-rolled `JSON.stringify` (`src/webhook/transformer.ts`) doesn't escape strings — `'\\"'` inside the TS template literal reaches QuickJS as a bare `"`, and backslashes/newlines are never escaped. Any `error`/`messageId` containing a quote or newline (common in bounce text) fails `JSON.parse`, the webhook returns 500 and the message status is never updated.
- `apps/backend/entrypoint.sh` starts the server without `exec`, so `sh` is PID 1 and SIGTERM never reaches Node; Docker kills the container mid-send after 10 s. Even when the signal arrives, `shutdown` in `src/index.ts` calls `process.exit(0)` without waiting for an in-flight send or closing the HTTP server. Every deploy during a send produces the stranded-`PENDING` problem above.
- Web redirect loop: `Login` sends anyone with a `token` cookie to `/dashboard`, and `useSession` sends anyone without an `orgId` in localStorage back to `/`; neither routes to `/onboarding`. A user who signs up and leaves before creating an org (or clears localStorage) bounces forever until they delete the cookie by hand.
- `docker-compose.yaml` and `docker-compose.node.yaml` ship `JWT_SECRET: your_super_secret_jwt_key` (and Postgres `user`/`password`), and `src/constants.ts` accepts any non-empty secret. A stack started from the documented compose file signs sessions with a public key, so tokens can be forged.

## Medium

- `stats.getStats` computes every rate as `matching / totalMessages…` where the numerator filters on `sentAt` but the denominator counts on `createdAt`. A message created in one window and sent in the next is counted in different buckets, so open/click/delivery rates can exceed 100% or be understated. Tests pin the current behaviour.
- `sendMessages` computes `availableSlots` from the rate window, but the rate-window count includes `FAILED` and `COMPLAINED` (both in `processedMessages`), so failures consume send quota.
- `subscriber.import` now maps rows to `{ email, name, organizationId }`; phone/company/tags columns are silently dropped. Worth deciding whether they should land in `SubscriberMetadata` instead.
- `settings.updateSmtp` upserts on `where: { id: smtpSettings ? smtpSettings.id : "create-happens" }` — a sentinel string standing in for "no row". `SmtpSettings.organizationId` is not unique in the schema, so nothing prevents two SMTP rows per org if two updates race.
- The REST API has no rate limiting: a valid API key can hammer `/api/subscribers` unbounded.
- `GET /api/subscribers` accepts any positive `perPage`, so `?perPage=1000000` will attempt to serialize the whole org in one response.
- `src/cron/cron.utils.ts` keeps its lock state in a module-level `Map` with no reset/clear. Tests must use a unique job name each time, and a real job whose function never settles would be locked out forever with no timeout or recovery.
- `processQueuedCampaigns` keeps "log this once" flags per skip *reason* in a module-level object; they reset only when that reason next passes, so with several campaigns a recurring skip (missing content, no subscribers) can stay silent. Debugging a stuck campaign in production may show nothing.
- `tests/integration/user.test.ts` previously asserted `GET /` → 200 and had been failing silently (the whole suite was red before the test-suite plan). Worth checking nobody was relying on a green CI signal that never existed.
- Webhook events overwrite message status with no ordering guard (`src/webhook/processor.ts`): a late `delivered` turns `OPENED`/`CLICKED` back into `SENT`, and a `delayed`/`pending` event sets `PENDING`, which isn't a completed status, so the campaign can sit in `SENDING` indefinitely.
- The webhook handler discards `processWebhookEvent`'s result (404 message not found, 400 unknown event) and always responds and logs 200, so misconfigured transforms look healthy and providers never retry.
- Bounces and complaints never suppress the subscriber: `bounced`/`complained`/`spam` only set the one message's status, so later campaigns keep mailing them and sender reputation suffers.
- Hot columns are unindexed: `Message.campaignId`, `Message.subscriberId`, `Message.status`, `ListSubscriber.subscriberId` (the `(listId, subscriberId)` unique can't serve it), `Campaign.organizationId`, `List.organizationId`. Per-campaign counts, the cron queue scan and cascade deletes become sequential scans on the largest table.
- Nothing in the schema prevents duplicate messages: there is no `@@unique([campaignId, subscriberId])` on `Message`, so two overlapping `processQueuedCampaigns` runs (e.g. a second instance) both insert and both send.
- A campaign can stick in `CREATING` forever: it only moves to `SENDING` inside a batch that created at least one message, so if the remaining recipients disappear (unsubscribed, deleted, list deleted) the empty batch just `continue`s every second.
- `message.resend` resets any message to `QUEUED` regardless of state: a `PENDING` message is sent twice, cancelled campaigns and since-unsubscribed subscribers get mail, engagement status is lost, and a message whose `content` was nulled by `dailyMaintenance` goes out blank and is marked `SENT`.
- `processQueuedCampaigns` reads every existing `Message.subscriberId` for the campaign on every per-second pass, which `getSubscribersForCampaign` already excludes; on a 100k-recipient campaign that is ~1,000 passes each reading up to 100k rows.
- `campaign.get` loads every `ListSubscriber` row for the campaign's lists just to use `.length`, then runs a separate count per list, on every campaign page load.
- `subscriber.import` upserts with `update: sub`, and `sub.name` is `null` when the CSV has no name columns, so re-importing a plain email list wipes every existing subscriber's name.
- `subscriber.update` (TRPC) runs `Metadata: { deleteMany: {} }` when `metadata` is omitted, deleting all metadata, and its schema lacks the 64/256 length limits `create` enforces.
- `list.delete` has no guard for `SCHEDULED`/`CREATING`/`SENDING` campaigns; the `CampaignList` cascade silently drops that list's recipients from them.
- `user.login` (TRPC) has no rate limiting or lockout anywhere, so online password guessing is unlimited. Separate from the REST rate-limit entry above.
- REST double-opt-in: the user-supplied `name` goes into the verification email HTML unescaped, and `console.log("data", data)` writes subscriber PII to logs on every create (`src/api/server.ts`).
- A trailing slash in the org `baseURL` (the settings form accepts it) makes `processQueuedCampaigns` build `https://x.com//img/<id>/img.png` and `//unsubscribe`, which don't match the Express routes — opens are silently never recorded. Only the verify-email link strips the slash.
- The PWA service worker (`apps/web/vite.config.ts`) uses vite-plugin-pwa's default `navigateFallback: "index.html"` with no denylist, so in a browser that has opened the dashboard, navigating to `/docs`, `/api/...`, `/t/:id` or `/unsubscribe` on the same origin serves the SPA instead of hitting the server.
- Several web mutations have no `onError` and the `QueryClient` has no global handler, so failures are silent: signup, onboarding, list create/update, and the save-then-start in `campaign-actions.tsx` (a failed save just does nothing).
- `entrypoint.sh` has no `set -e`, so a failed `prisma migrate deploy` still starts the server on an unmigrated schema; compose's `depends_on: db` has no health condition, and `prisma.$connect().then(...)` in `src/index.ts` has no `.catch`.
- Docker images (`Dockerfile`, `Dockerfile.node`) never set `USER`; the server, cron and the QuickJS sandbox run as root.
- `.github/workflows/docker.yaml` derives image tags from `package.json`, not the git tag: a manual run from any branch overwrites `:<version>` and `:latest` with unreleased code, a tag push without a version bump overwrites the previous release's images, and image builds don't wait on tests.

## Low

- Org-membership failures are inconsistent across routers: `list.create`/`list.list` throw `NOT_FOUND`, while `list.get`/`update`/`delete` and every subscriber procedure throw `UNAUTHORIZED`. The tests pin current behaviour.
- `webhook.logs` scopes by `Webhook.organizationId`, so another organization's `webhookId` returns an empty page rather than `NOT_FOUND`. Safe, but indistinguishable from "no logs yet".
- The transformer's "fall back to the raw body when transform returns undefined" path is dead code: the wrapper copies the result with `for (const key in result)`, so `undefined` becomes `{}`, which then fails schema validation with a 500. The 400/fallback branch can never be reached. Test pins the actual behaviour.
- `dailyMaintenance` falls back to `?? 30` days for orgs with no `GeneralSettings` row, disagreeing with the schema default of 90 used by `cleanupWebhookLogs`.
- `Mailer.sendEmail` throws on transport failure rather than returning `{ success: false }`; callers in `cron/sendMessages.ts` and `campaign/mutation.ts` rely on that throw. The mixed success-value/exception contract is easy to misuse.
- Both tracking endpoints respond *before* their database write finishes. Tests must poll (`@helpers/wait-for`), and any that do not can leak a write into the next test's freshly reset database.
- `authenticateApiKey` updates `lastUsed` without awaiting and only logs on failure, so `lastUsed` is best-effort, not guaranteed, and tests must poll for it.
- CI `on: push` has no branch filter, so the suite runs on every branch push (and twice for PR branches in the same repo). Narrow to `main` + `pull_request` if the minutes matter.
- CI `JWT_SECRET` falls back to the literal `ci-jwt-secret` when the `TEST_JWT_SECRET` secret is unset, so CI never fails loudly if the secret goes missing.
- CI assumes migrations alone produce a usable schema (no seed step), and `setup.ts` re-runs `prisma migrate deploy` per test file, adding ~1s per file.
- The unit tests under `src/**` still load `tests/integration/helpers/setup.ts`, so each one pays a full DB reset it does not need. Worth a separate vitest project for unit vs integration if the suite gets slow.
- Vitest emits `ENOENT ... prisma/client/runtime/library.js.map` warnings on every run. Harmless (missing sourcemap in the generated client) but noisy.
- `user.signup` accepts a 1-character password (`z.string().min(1)`), while `changePassword` requires 8.
- `settings.getSmtp` and `updateSmtp` return the full `SmtpSettings` row, including the SMTP `password`, to the browser (it lands in the settings form). Members only, but the credential is always readable client-side.
- `list.get` loads every `ListSubscriber` with the full `Subscriber` (including `emailVerificationToken`), unpaginated, *before* the membership check — any logged-in user can make the server load an arbitrarily large list by id. The web app doesn't call it.
- The "recipients" stat SQL (`prisma/sql/countDistinctRecipients*.sql`) counts subscribers across all message statuses, including `QUEUED`, `CANCELLED` and `FAILED`, unlike every other stat which filters to `processedMessages`.
- Placeholder values are passed to `String.replace` as the replacement string, so `$&`, `` $` ``, `$'` and `$$` are interpreted ("Save $$$" becomes "Save $$"; a subscriber named `$'` duplicates the rest of the document), and values are not HTML-escaped.
- `sendMessages` checks `message.tries >= maxRetries` against the pre-increment count, so `maxRetries = N` gives N+1 attempts.
- Templates can be edited or deleted (`onDelete: SetNull`) while a campaign using them is `CREATING`; later batches render with the new template or none, and drafts lose their template silently.
- `email-preview.tsx` sets `target="_blank"` on every link but the iframe sandbox lacks `allow-popups`, so links in previews do nothing.
- `.dockerignore` doesn't exclude `.pnpm-store/`, `.claude/` or `plans/`, so `docker compose up --build` uploads gigabytes of context and `COPY . .` bakes them into the image.
- `CLAUDE.md` documents `./scripts/release.sh`, but the script was deleted in `5741559` ("Knip & Clean Ups"); only `scripts/gen-container-img-tags.ts` remains.
